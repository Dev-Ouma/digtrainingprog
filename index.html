    Session 01

    Introduction

    Welcome to the digitisation team. You are joining an exercise that puts every 4.2 semester undergraduate course into Moodle in a consistent, accessible, student-ready form. This session sets out what that means in practice.

    Learning objectives

    • Explain the scope and purpose of the digitisation exercise
    • Describe what a completed digitised module looks like
    • Identify the roles of technical, non-technical and multimedia digitisers
    • State your own targets, timelines and reporting line

    How the programme runs

    1. 1
      You are assigned modules. Each digitiser receives named modules with a due date. Nothing is picked up informally.
    2. 2
      You digitise to the standard. The same template, naming and formatting rules apply to every module, whoever builds it.
    3. 3
      You self-check, then submit. Run the checklist against your own work before it goes for validation.
    4. 4
      Validation returns corrections. You close them out and the module is signed off and published.

    Key takeaways

    • Consistency across modules matters more than individual flair
    • A digitised module is finished only when it passes validation
    • Your reporting line is your team lead, then the Directorate of ICT

    Tip

    Open a module that has already been signed off and read it as a student would. That is the target you are building towards.

    Next: Preparing the environment

    Session 02

    Preparing the environment

    Before you touch content, get Moodle and your workstation into a state where the work is fast and repeatable. Most lost time on this programme comes from a badly set up environment.

    Learning objectives

    • Navigate the Moodle interface and switch roles confidently
    • Create a course, configure its settings and set a course image
    • Organise course categories and manage roles and permissions
    • Apply the folder structure and file naming conventions used on the programme

    What you need in place

    Tap or hover a card to see the detail.

    Required software

    Current Chrome or Edge, Office or LibreOffice, a PDF reader, VS Code for HTML and SCSS, Panopto recorder, and an approved AI assistant.

    Folder structure

    /CODE-Title/ then 01-source/, 02-working/, 03-media/, 04-final/. Never edit inside 01-source.

    File naming

    CODE_topic_v03.docx — lower case, underscores, two-digit version, no spaces, no personal names, no “final_final”.

    System requirements

    8 GB RAM or more, a stable connection for uploads, headphones for captioning, and your OUK account with the editing-teacher role.

    Key takeaways

    • Switch role to Student before you decide a page is finished
    • Categories carry meaning — put the course where a student would look for it
    • A file named properly today saves an hour of searching next week

    Watch out

    Editing mode off is the most common reason people think Moodle is broken. Check the toggle first.

    Session 03

    Core workflow

    This is the heart of the job: taking a Word, PDF or HTML source and turning it into a structured Moodle module. AI does the first pass. You are the expert who reads it through.

    Learning objectives

    • Convert source notes into Moodle content with AI assistance
    • Chunk lengthy content into sections a student can finish in one sitting
    • Build reusable content templates, including Canvas templates for H5P.org
    • Apply consistent CSS and SCSS standards with uniquely named divs
    • Choose the right resource or activity for each purpose

    The conversion pipeline

    1. Readwhole source
    2. Cleanstrip artefacts
    3. ConvertAI first pass
    4. Verifyyou, the expert
    5. Chunkone idea each
    6. Templateshared classes
    7. InteractH5P or quiz

    The seven-step conversion

    1. 1
      Read the source first. Skim the whole document before converting anything. You cannot chunk what you have not read.
    2. 2
      Clean the source. Strip page numbers, headers, footers and scanned artefacts. Rubbish in, rubbish out.
    3. 3
      Convert with AI. Prompt for structured HTML with headings, lists and tables. Ask for the structure, not a rewrite of the scholarship.
    4. 4
      Read it through as the expert. Check every fact, formula and figure against the source. AI output is a draft, never a deliverable.
    5. 5
      Chunk into sections. One idea per page or book chapter, with objectives at the top and a check for understanding at the end.
    6. 6
      Apply the template. Drop the content into the approved template. Use the shared classes, and give each div a unique, meaningful name.
    7. 7
      Add interaction. An H5P element, a glossary entry or a short quiz turns a page of reading into a lesson.

    Choosing the right building block

    Resources — for content

    • Page a single screen of content
    • Book a multi-chapter topic
    • File one downloadable document
    • Folder a set of related files
    • URL a link out
    • Label a heading or note in the course page
    • IMS Content Package imported packaged content
    • SCORM Package tracked packaged content
    • H5P Interactive Content interaction inside the page
    • Database a structured collection students add to
    • Glossary defined terms, linked automatically

    Activities — for doing

    • Assignment submitted and marked work
    • Quiz auto-marked assessment
    • Forum asynchronous discussion
    • Choice a single quick poll
    • Feedback a custom questionnaire
    • Survey standard instruments
    • Workshop peer assessment
    • Wiki co-authored pages
    • Chat live text sessions
    • Lesson branching, conditional paths
    • Attendance session registers
    • H5P activity graded interactive tasks

    Common mistakes

    Word carries hidden styles that break the Moodle theme and fail contrast checks. Paste as plain text, then apply the template classes yourself.

    AI reorders, summarises and occasionally invents. You are the subject expert on that module — read every line against the source before you save.

    If a student cannot finish a section in one sitting, it is too long. Split it into a Book with chapters, or several Pages with a clear order.

    Generic names like .box collide with the theme and with other modules. Prefix everything: .ouk-mod-intro, .ouk-mod-callout.

    Session 04

    Practical exercise

    Hands on the keyboard. You will build one complete section of your assigned module, then assess it. Work at your own pace and tick each task off as you finish it.

    Learning objectives

    • Build a branded module template with objectives, content and a check for understanding
    • Create question bank categories and items across the main question types
    • Assemble a randomised quiz with feedback configured
    • Embed one piece of multimedia correctly, with captions

    Question types at a glance

    Aim for at least four different types in every question bank category.

    Multiple choice

    One correct option, plausible distractors.

    Matching

    Pairs a term with its definition or example.

    Embedded answers (Cloze)

    Gaps inside a passage, marked automatically.

    Drag and drop

    Onto text, onto an image, or into markers.

    Numerical & STACK

    Tolerances, units, and full maths marking.

    CodeRunner

    Runs student code against your test cases.

    Practice tasks

    Tick each one as you complete it. Your progress is shown on the right.

    Progress tracker

    0%

    0 of 10 tasks complete

    Tip

    Build the quiz before you polish the styling. Assessment exposes gaps in the content faster than proofreading does.

    Key takeaways

    • Question categories named after sections make randomisation trivial later
    • Every image needs alternative text at the moment you insert it, not afterwards
    • The student view is the only view that counts

    Session 05

    Quality assurance

    A module is not finished when it looks finished. This session covers multimedia handling, HTML and accessibility standards, copyright, and the review that every module passes through.

    Learning objectives

    • Handle video, audio and images to the programme's technical standards
    • Write clean, responsive HTML that meets WCAG accessibility requirements
    • Apply copyright, Creative Commons and OER attribution rules correctly
    • Run the validation checklist and close out returned corrections

    Multimedia

    Upload video through Panopto; embed YouTube or Vimeo rather than uploading copies. Record lectures with a headset, add captions to every video, optimise and resize images before upload, and convert audio to a web format.

    HTML and styling

    Headings in order, real lists, real tables with header cells, descriptive link text, responsive images and no fixed pixel widths. Keep CSS and SCSS to the shared classes and give every div a unique prefixed name.

    Accessibility (WCAG)

    Alternative text on images, a logical order for screen readers, sufficient colour contrast, accessible tables and PDFs, full keyboard navigation, and captions on every video. Colour alone never carries meaning.

    Copyright

    Know what you may use: copyright basics, Creative Commons licence types, Open Educational Resources, attribution requirements, fair use and the restrictions that come with each licence. Attribute at the point of use.

    Contrast, in practice

    9.1:1

    Deep teal #02505E on white. Passes AA and AAA at every size.

    Use this for body text
    4.95:1

    Brand teal #037B90 on white. Passes AA for body text, but falls short of AAA.

    Body text, AA only
    2.5:1

    Gold #FF7F50 on white. Below 3:1, so it fails even for large headings — keep it for borders, fills and icons that carry no meaning.

    Never for text

    The validation process

    1. 1
      Self-check. Run the checklist yourself. Modules that arrive unchecked are returned without review.
    2. 2
      Submit for validation. Log the module in the tracker with its version and date.
    3. 3
      Technical validation. A validation expert reviews structure, assessment, media and accessibility.
    4. 4
      Corrections returned. Each finding is specific. Fix it, note what you changed, resubmit.
    5. 5
      Sign-off. The module is marked complete and released to the course.
    6. 6
      Escalate what you cannot fix. A missing source file or an unclear diagram goes to your team lead the same day, not next week.

    Key takeaways

    • Accessibility is built in as you go; it cannot be retrofitted cheaply
    • An unattributed image is a legal problem, not a formatting problem
    • Returned corrections are information about the standard, not criticism of you

    Watch out

    Never miss a section. A module that is 90 percent complete is not partly done — it is not done.

    Session 06

    Completion & certification

    The morning ends here and the work begins. This session covers the final assessment, how you submit, what certification requires, and how support continues once you are digitising live.

    Learning objectives

    • Complete the final assessment and know the pass standard
    • Submit your practice module through the correct channel
    • State the requirements for certification on the programme
    • Know where to get help once you are working on live modules

    Final assessment

    A short practical review of the section you built: structure, question bank, media and accessibility. Assessed against the same checklist validators use.

    Submission

    Submit through the tracker with the module code, version number and date. Attach nothing by email — the tracker is the record.

    Certification

    Attendance for the full session, a submitted practice section that passes review, and the ten practice tasks completed.

    Support from noon

    You are paired with an experienced digitiser and issued a live module. Ask early — a question at 12.30 is cheaper than a rebuild at 4.00.

    Closing remarks

    You now know the workflow, the standards and where the traps are. What separates a good digitiser from an average one is not speed — it is attention to detail, and never leaving a section half done. Take the checklist seriously, ask questions early, and the modules you publish will hold up for years.

    Urgent Directive · All Digitisation Teams

    Course Navigation & Resource Display Standards

    Hi Team: We must urgently address a critical navigation challenge in terms of our course programming across all digitised modules. Normally, when a student is progressing through a course, the main course index tab should remain undisturbed as one navigates through other elements. Opening resources directly on the same main page overwrites the index and disorients learners. Resources must either appear within the same frame and well embedded, or open in a new tab so the main tab is untouched. Treat this as urgent across all courses you are working on.

    01 Critical Rule

    Course Index Preservation

    The learner’s primary course window must remain anchored and untouched at all times.

    • The Challenge: When an article or file launches in the same window, it hijacks the student’s course index, destroys reading state, and requires repeated back-button clicks to restore.
    • The Requirement: Never overwrite the active course tab. Every supplementary reading, file, or activity must open non-destructively.
    02 Display Architecture

    Embed or target="_blank"

    Every file, article, and resource must implement one of two approved pathways:

    • Option A — In-Frame Embed: For files uploaded to SOMAS, configure Appearance → Display: Embed so the document renders inside the Moodle frame with breadcrumbs intact.
    • Option B — New Window / Tab: For hyperlinks and HTML articles, append target="_blank" rel="noopener noreferrer" to open the destination safely in a new tab.
    03 Typography Standard

    Strip Inline font-family

    Avoid hardcoded font types — let the system typography render naturally.

    • The Issue: Hardcoding font-family: Calibri, Arial, sans-serif; overrides university design rules, breaks responsive mobile rendering, and creates jarring contrast bugs in dark mode.
    • The Standard: Delete font-family from your style attributes. Let SOMAS and device system fonts render text while retaining custom card borders, gradients, and padding.
    Option A · SOMAS File Appearance Settings

    Configuring In-Frame Resource Embedding

    When adding a File resource in SOMAS / Moodle, avoid default display settings that force automatic downloads or overwrite the course index. Configure the Appearance panel exactly as specified below:

    1
    Set Display dropdown to "Embed": Renders the document, PDF, or interactive asset directly inside the SOMAS course content window so the student never leaves the page.
    2
    Check "Display resource description": Displays your framing rationale, reading instructions, and prompt guidance directly on the course page alongside the resource.
    3
    Leave file metadata unchecked: Keep "Show size", "Show type", and "Show upload/modified date" unticked unless specifically needed, preserving a clean and focused visual hierarchy.
